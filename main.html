02 — Authentication Patterns

OAuth2 dominates, but almost never alone

Nearly half of all 100 apps support both OAuth2 and a simpler API-key/token path — meaning most integrations don't have to solve a full OAuth consent-screen flow just to get read access. Pure API-key products cluster in developer infra and data/scraping tools; pure OAuth2 clusters in customer-facing SaaS with per-user permission models.

08 — Agent Workflow

How the research agent works

Input

100 app names across 10 categories, mixed auth patterns on purpose.

→

Research Agent

Searches official docs, extracts auth/API surface/dev-access, detects existing MCP servers.

→

Verification Agent

Re-checks uncertain fields against an independent source, flags disagreements instead of averaging.

→

Human Review

Spot-checks a sample (adversarial + random), corrects the record, decides "flag for outreach" vs "guess."

Stack: Python + Composio SDK (browser/search tool execution) + an LLM for structured extraction, output as JSON end-to-end. What it does: for ~75 well-documented major platforms, a knowledge-only extraction pass was fast and accurate. Where it needed a human: every app that was obscure, ambiguous, or where a wrong answer would look plausible (~25 apps) got a live-search verification pass — and 2 of those (Waterfall.io, iPayX) still couldn't be resolved and are honestly flagged rather than guessed. See research_agent.py and README.md in the source repo for the runnable pipeline design.

Using the full research table

  • Search box — matches against app name, category, description, auth method, and blocker text simultaneously.
  • Category / Readiness / Confidence dropdowns — combine with search and with each other; all filters apply as an AND.
  • Confidence column — this is the honesty signal. verified = checked against live docs during this run. known = well-documented major platform, high-confidence from training knowledge, not independently re-checked this run. inferred = uncertain, flagged rather than guessed — treat these as "needs a human" before you rely on them.
  • Evidence column — the docs URL or source backing that row's findings; not found — manual check needed means exactly that, honestly, rather than a fabricated link.

Glossary

🟢 Easy build
Self-serve auth, documented REST/GraphQL API, no partner gate — an agent toolkit could plausibly ship this week.
🟡 Buildable with limits
Technically possible today but something slows it down: a review/approval step, a paid-tier gate, or a thinner action surface.
🔴 Hard / blocked
No self-serve path at all, no discoverable public API, or not a hosted service (e.g. a local CLI).
Dev Access
Whether a developer can get credentials themselves today: fully public, public-but-limited, enterprise/partner-gated, or no API.
API Score (1–5)
Rough maturity read on docs quality, CRUD coverage, webhook support, and SDK availability.
MCP status
Whether an official, community, or no MCP server currently exists for this app — checked as of this run; this is the fastest-moving field in the dataset.
Confidence
verified (live-checked) / known (trained knowledge, high confidence) / inferred (uncertain, flagged for follow-up).

Pipeline in detail

Four stages, described fully in research_agent.py: (1) Research Agent searches official docs for a given app name; (2) Extraction Agent turns raw doc text into the structured schema below using an LLM structured-output call; (3) Verification Agent independently re-checks any field marked uncertain against a second source; (4) Human Review spot-checks a sample and corrects the record.

For this run specifically: stages 1–2 ran as a knowledge-only pass for ~75 mainstream, well-documented platforms (fast, accurate, no search cost). Stage 3 (live search verification) ran for real on ~25 apps flagged as obscure or ambiguous — see the Verification section above for the actual before/after corrections. Stage 4 is this document plus the confidence field on every row.

  "name": str, "category": str, "url": str, "desc": str,

  "score": int,       # 1-5 API maturity

FAQ

Why isn't every row "verified"?Verifying all 100 with live search wasn't the efficient or honest choice — the ones already well-documented in training data (Slack, Stripe, GitHub) don't need re-checking, and spending search budget there would starve the apps that actually needed it. The confidence field tells you exactly which is which.
Why are two apps still unresolved?Waterfall.io and iPayX had no discoverable public developer docs after searching. Guessing would have looked more complete but been less true — they're flagged for a human to contact the vendor directly instead.
How current is the MCP column?As of this run's date. New official MCP servers ship weekly across the ecosystem; treat "none found" as "none found on this date," not "will never exist."
Can I filter to just the apps that need outreach?Yes — set the Full Table readiness filter to 🔴, or read section 05 directly, which is the same 🔴 set with suggested next steps attached.
